# Teoría: Issues, Projects y colaboración

## ¿Qué es un Issue?

Un issue es un registro de trabajo dentro de GitHub. Puede representar:

- una tarea
- un error
- una mejora
- una pregunta
- una discusión sobre algo pendiente

## ¿Para qué sirven los Issues?

Los issues ayudan a:

- registrar trabajo pendiente
- dar visibilidad a errores o mejoras
- asignar responsabilidades
- priorizar trabajo
- mantener trazabilidad

## Diferencia entre Issue y Pull Request

- Issue: describe un problema, tarea o necesidad
- Pull Request: propone cambios concretos para resolver o implementar algo

En muchos casos, un pull request nace a partir de un issue.

## ¿Qué son las Labels?

Las labels son etiquetas que ayudan a clasificar issues y pull requests.

Ejemplos comunes:

- `bug`
- `enhancement`
- `documentation`
- `good first issue`
- `priority: high`

## ¿Qué son los Milestones?

Los milestones permiten agrupar issues o pull requests bajo un objetivo o entrega común.

Ejemplos:

- `MVP`
- `v1.0`
- `Módulo 3 completado`

## ¿Qué es GitHub Projects?

GitHub Projects es una herramienta para organizar y visualizar trabajo, normalmente en forma de tablero.

Puede usarse para:

- priorizar tareas
- mover trabajo entre estados
- ver progreso
- gestionar backlog

## Flujo común de trabajo

Un flujo sencillo puede verse así:

1. crear un issue
2. clasificarlo con labels
3. asignarlo a un milestone o project
4. crear una rama para resolverlo
5. abrir un pull request
6. hacer merge
7. cerrar el issue

## Buenas prácticas

- crear issues claros y específicos
- usar títulos descriptivos
- no mezclar varios problemas en un mismo issue
- usar labels consistentes
- vincular PRs con issues cuando corresponda
- cerrar issues cuando el trabajo termine

## Errores comunes

- crear issues vagos
- no actualizar el estado del trabajo
- no usar labels
- no relacionar issues con cambios reales
- usar PRs como si fueran issues
